# 求职面试助手优化专题三：结构化结果展示、评测与可观测性

## 当前现状

当前已经完成的部分：

- `resume_match` 有专门的结构化卡片
- Agent 执行轨迹已经可以在前端看到
- 后端也补了 Tool / MCP / Skill 调用日志

但还存在明显缺口：

- `resume_rewrite` 还是纯文本
- `interview_followup` 还是纯文本
- 没有固定评测样例
- 没有 Tool 级别的统计指标

## 这一阶段的目标

把“后端能力”和“前端体验”对齐。

用户不应该只看到一大段 Markdown，而应该看到：

- 结果卡片
- 执行轨迹
- 下一步动作
- 一键复用结果

## 前端结果展示建议

### 1. 简历改写卡片

建议拆成 4 个区域：

- 改写思路
- 当前问题
- 可直接复用的改写版本
- 建议补充的信息 / 关键词

推荐交互：

- 一键复制改写版本
- 一键继续生成“面试追问”

### 2. 面试追问卡片

建议拆成 3 个区域：

- 高频追问
- 作答框架
- 风险点

推荐交互：

- 一键复制问题
- 一键继续做“模拟回答”

### 3. 执行轨迹面板增强

当前执行轨迹已经能显示：

- 调了哪些 Tool
- 调了哪些 MCP

下一步可以继续增强：

- 显示每一步耗时
- 显示调用顺序编号
- 区分“主 Agent 调用”和“子 Agent 调用”

## 后端协议建议

当前 `resume_match` 已经有结构化 event。

建议把另外两个 Tool 也升级成：

- 既保留 LLM 可读的文本返回
- 又额外发送结构化事件给前端

这样可以做到：

- 对模型：仍然是普通 Tool 结果
- 对前端：可以渲染卡片，不依赖 Markdown 解析

## 为什么这一步重要

因为“大模型应用开发”不是只看后端调用了模型。

真正成熟的项目，一定会处理：

- 流式输出
- Tool 结果结构化
- 前后端协议
- 用户交互闭环

如果这一步做完，你在面试里能讲：

`我不仅做了 Tool Calling，还把 Tool 结果设计成结构化事件流，前端按不同 Tool 类型做专门渲染。`

这个表述会明显更专业。

## 评测体系建议

### 1. 固定样例集

建议准备 6 到 10 条固定输入：

- 2 条岗位匹配
- 2 条简历改写
- 2 条面试追问

每条样例保存：

- 输入
- 期望输出方向
- 实际输出
- 是否通过

### 2. 基础评测维度

对于 `resume_match`：

- 是否识别出岗位关键词
- 是否指出真实缺口
- 是否有可执行建议

对于 `resume_rewrite`：

- 是否保留原始事实
- 是否减少空话套话
- 是否强化岗位相关表达

对于 `interview_followup`：

- 问题是否具体
- 回答框架是否可复用
- 是否覆盖业务、技术、贡献、结果

### 3. Tool 调用统计

建议统计：

- Tool 调用次数
- 成功率 / 失败率
- 平均耗时
- 最常被调用的 Tool

这些数据未必一开始就要做成后台页面，但至少应该能在日志或简单报表里看到。

## 从简历视角看，这一步能带来的提升

做完之后，你的项目描述可以从：

`实现了求职场景的 Tool Calling`

升级成：

`设计并实现面向求职场景的结构化 Tool 输出协议，结合 SSE 事件流与前端卡片化渲染，提升 Agent 结果的可读性、可操作性与可观测性。`

## 推荐落地顺序

1. 给 `resume_rewrite` 增加结构化 event
2. 给 `interview_followup` 增加结构化 event
3. 前端分别做两张结果卡片
4. 补固定评测样例
5. 记录 Tool 调用耗时和成功率

## 这一阶段的核心原则

不要只追求“模型回答得更多”。

要追求：

- 输出更稳定
- 前端更可用
- 调用链更可见
- 结果更方便演示和复用
