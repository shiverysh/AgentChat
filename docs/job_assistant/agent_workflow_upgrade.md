# 求职面试助手优化专题二：多步工作流与 Agent 编排

## 当前问题

当前的求职助手虽然已经具备多个 Tool：

- `resume_match`
- `resume_rewrite`
- `interview_followup`

但整体交互仍然偏单轮：

- 用户输入一句话
- Agent 决定调一个 Tool
- Tool 返回结果
- 对话结束

这更像“带 Tool 的聊天”，还不够像“多步 Agent Workflow”。

## 这一阶段的目标

把求职助手升级成一个更明确的多步流程型 Agent。

推荐工作流：

1. 识别用户任务意图
2. 抽取输入材料
3. 判断信息是否充足
4. 选择调用匹配 / 改写 / 面试追问 Tool
5. 汇总结果
6. 给出下一步建议

## 推荐拆分的任务类型

### 类型一：岗位匹配分析

条件：

- 用户同时提供 JD 和简历 / 项目经历

流程：

1. 检查 JD 是否存在
2. 检查简历内容是否存在
3. 调用 `resume_match`
4. 输出匹配结论
5. 提示用户是否继续改写项目经历

### 类型二：简历改写

条件：

- 用户提供项目经历或简历片段
- 明确表示要改写或优化

流程：

1. 识别目标岗位
2. 抽取原始项目描述
3. 调用 `resume_rewrite`
4. 输出可直接复用的改写结果
5. 提示是否继续生成面试追问

### 类型三：面试追问准备

条件：

- 用户提供项目经历
- 明确表示想准备面试

流程：

1. 抽取项目内容
2. 识别目标岗位方向
3. 调用 `interview_followup`
4. 输出追问和作答框架
5. 提示可以继续做模拟面试

## 建议新增一个“任务路由层”

当前主 Agent 是直接根据对话上下文选 Tool。

下一步建议新增一个更轻量的“任务路由层”，它不一定要单独变成新服务，也可以先放在 prompt 层或 workflow 层。

它主要负责做三件事：

1. 判断当前属于哪种任务
2. 判断缺哪些必要字段
3. 决定后续调用顺序

## 两种实现路线

### 路线 A：轻量级编排

适合当前仓库快速落地。

做法：

- 继续使用现在的 GeneralAgent
- 通过 system prompt 强化“先判断任务类型，再调对应 Tool”
- 必要时加一个轻量路由 Tool

优点：

- 改动小
- 易于接入现有架构

缺点：

- 工作流的状态流转不够显式
- 可控性一般

### 路线 B：LangGraph 工作流

适合把项目往“更强 Agent 感”方向推进。

做法：

- 用 LangGraph 定义显式节点
- 节点示例：
  - `classify_task`
  - `extract_resume`
  - `run_resume_match`
  - `run_resume_rewrite`
  - `run_interview_followup`
  - `finalize_response`

优点：

- 结构清晰
- 更适合展示多步 Agent
- 更容易加状态管理和错误恢复

缺点：

- 改动更大
- 需要重构一部分对话链路

## 推荐你当前采用的策略

如果你是为了把项目继续打磨成简历项目，我建议：

### 第一阶段

先做轻量级编排。

目标是让求职助手表现出更清晰的多步决策，而不是立刻大规模重构。

### 第二阶段

如果时间和精力够，再把求职助手单独抽成 LangGraph 工作流。

这样你在面试时可以分两层讲：

1. 先做了场景化 Tool + Agent 集成
2. 后续又把求职助手升级成显式多步工作流

## 前端应该怎么配合

如果后端开始变成多步工作流，前端不能再只展示最终文本。

建议前端展示：

- 当前任务类型
- 当前步骤
- 已完成步骤
- 当前调了哪个 Tool
- 下一步建议

这样用户才能真正感知到：

这不是一个普通聊天机器人，而是一个“会分步完成任务的 Agent”

## 面试时能怎么讲

如果你做完这一步，可以把项目描述升级成：

`围绕求职辅导场景设计多步 Agent Workflow，将岗位匹配、简历改写、面试追问拆分为独立步骤，并通过 Tool Calling 完成任务编排与结果汇总。`

比起“我写了几个 Prompt Tool”，这个说法更像大模型应用开发。

## 这一步最重要的产出

不是代码量，而是：

- 任务拆解逻辑更清晰
- Tool 之间的关系更清晰
- Agent 的“自主流程感”更强

## 建议的落地顺序

1. 把任务类型先明确成 3 类
2. 给每类任务写清楚“触发条件 + 所需输入 + 对应 Tool”
3. 在 prompt / route 中先实现轻量编排
4. 之后再考虑迁移到 LangGraph 显式节点
