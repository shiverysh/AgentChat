# 求职面试助手项目简历版梳理

## 1. 项目名称与定位

**项目名称：** 求职面试助手（基于 AgentChat 的大模型应用二次开发）

**一句话定位：**

基于开源 AgentChat Agent 基座，围绕求职场景完成 Tool Calling、MCP 集成、文档解析、SSE 执行轨迹展示和前端工作台联动，形成一条可演示、可讲清、可写进简历的完整 Agent 应用链路。

**适合投递岗位：**

- 大模型应用开发实习生
- AI Agent / LLM 应用开发实习生
- AI 产品研发 / 智能体应用工程实习生

## 2. 项目背景

原项目 `AgentChat` 本质上是一个通用 Agent 平台，底座已经具备 Agent、Tool、MCP、流式对话、前后端分层等通用能力。  
本次工作的重点不是“从零自研一个 Agent 平台”，而是**基于开源基座做面向求职场景的二次开发和工程落地**，把原本偏通用的平台收敛成一个更贴近“大模型应用开发实习生”岗位的垂直 Agent 应用。

这次二开的核心目标有三点：

1. 把项目从“通用聊天平台”改造成“有明确业务闭环的求职助手”。
2. 把 Agent 的能力从纯对话扩展到 Tool Calling、MCP 调用、文档解析、外部协同。
3. 把结果从 Markdown 文本升级为前端可见的执行轨迹、结构化结果卡片和工作台数据面板。

## 4. 完整 Agent 开发链路

这份项目最适合讲的不是“我写了几个 Prompt”，而是下面这条完整链路：

### 4.1 用户输入阶段

用户在前端输入岗位 JD、简历内容，或直接上传 PDF / DOCX / TXT / MD 文件。

### 4.2 文件解析阶段

后端先做轻量正文抽取，把简历文本注入模型上下文：

- PDF：本地文本抽取
- DOCX：文档正文读取
- TXT / MD：直接读取

如果是复杂版式、扫描件或更高质量解析需求，Agent 可进一步调用 `mineru_parse`，通过 MinerU 远程 API 获取更完整的解析结果。

### 4.3 Agent 决策阶段

主 Agent 根据用户意图和上下文做任务路由：

- 想看岗位和简历匹配度时，调用 `resume_match`
- 想把项目经历改成更适合投递的表达时，调用 `resume_rewrite`
- 想准备技术追问和面试问答时，调用 `interview_followup`
- 需要外部沉淀或协同结果时，进一步调用 MCP

### 4.4 Tool Calling 阶段

业务分析类能力通过普通 Tool 执行：

- `resume_match`：输出匹配度、优势、缺口、修改建议
- `resume_rewrite`：输出更适合岗位的简历改写版本
- `interview_followup`：输出面试追问点、回答框架和准备建议
- `mineru_parse`：输出解析文本和解析元数据，供后续工具继续消费

### 4.5 MCP 调用阶段

当结果需要沉淀成外部资产时，主 Agent 调用独立 MCP Server：

- 求职工作台 MCP：保存简历版本、记录岗位投递、生成面试计划、保存追问笔记
- 飞书 MCP：创建飞书文档、写入正文、返回文档链接、创建日历和日程

这里最关键的点是：

- Tool 更偏“生成与分析能力”
- MCP 更偏“跨系统协同与结果落地”

### 4.6 SSE 事件回传阶段

后端通过 SSE 把模型思考过程中的关键事件实时回传到前端，包括：

- Tool 调用事件
- MCP 调用事件
- 工具结果事件
- 最终回答事件

### 4.7 前端展示阶段

前端不是只展示 Markdown 文本，而是做了更接近产品化的结构化承接：

- 执行轨迹面板：显示调用了哪些 Tool / MCP
- 结果卡片：显示简历匹配、改写结果、面试追问
- 求职工作台：展示投递记录、简历版本、面试计划、追问笔记
- 飞书状态提示：提示当前是否具备个人空间同步能力

### 4.8 用户追问闭环

用户可以基于当前结果继续发起下一轮请求，例如：

`岗位匹配 -> 简历改写 -> 面试追问 -> 同步到飞书 -> 生成面试计划`

这条链路体现的是一个真实的 Agent 应用闭环，而不是一次性问答 Demo。

## 5. 项目技术亮点

这部分适合在简历和面试里重点强调。

### 5.1 场景化 Agent 设计

- 基于通用 Agent 基座做垂直场景收敛
- 围绕求职场景定义默认 Agent、默认 Tool、默认 MCP
- 让项目具备明确业务边界，而不是泛化聊天

### 5.2 Tool Calling 工程化落地

- 自定义 `resume_match`、`resume_rewrite`、`interview_followup`
- 输出尽量结构化，便于前端卡片渲染
- 让 Agent 从“只会回答”升级为“会调度任务能力”

### 5.3 文档解析链路

- 打通文件上传到模型消费的全流程
- 轻量解析负责快速可用
- MinerU 负责复杂文档增强解析
- 支持按文件类型自动选择解析模型

### 5.4 MCP 标准协议接入

- 使用独立 `FastMCP stdio` 服务承接求职工作台能力
- 飞书能力也走 MCP，而不是简单本地函数拼接
- 实现 Agent 调度能力和外部系统写入的解耦

### 5.5 前后端联动与可观测性

- 后端通过 SSE 输出中间执行事件
- 前端展示 Tool / MCP 调用轨迹
- 结果以结构化卡片和工作台面板承接，增强可解释性和可演示性

### 5.6 工程稳定性修复

- 修复一批初始化、配置、会话、MCP 接入和滚动展示问题
- 飞书 MCP 从远程黑盒 SSE 切到本地 `stdio`
- 支持区分 `user_access_token` 和应用身份，避免“API 成功但用户不可见”的误判

## 10. 技术追问展开讲法

如果面试官继续追问，可以按下面方式展开：

### 10.1 为什么要分 Tool 和 MCP

- Tool 更适合做分析和生成，比如简历匹配、简历改写、面试追问
- MCP 更适合对接独立外部能力，比如工作台数据落库、飞书文档和日历同步
- 这样主 Agent 只负责理解意图和调度能力，业务能力和外部系统能力解耦更清晰

### 10.2 为什么还要接 MinerU

- 轻量解析适合普通 PDF / DOCX，速度快、成本低
- 复杂排版、扫描件、HTML 文档更适合交给 MinerU
- 把 MinerU 封装成 Tool 后，Agent 可以按需调用，而不是所有文件都走重解析

### 10.3 这个项目的 Agent 属性体现在哪里

- 主 Agent 会根据用户意图决定调用哪个 Tool
- 当需要把结果沉淀成外部资产时，会进一步调用 MCP
- 前端能看到完整的执行轨迹，而不是只看到最终答案
- 因此它不是“聊天页面 + 提示词”，而是具备任务分解和能力编排的 Agent 应用

### 10.4 你在这个项目里最有价值的工作是什么

- 把通用平台收敛成了一个有业务闭环的垂直应用
- 把 Tool、MCP、文档解析、前端展示和外部协同真正串成了一条完整链路
- 让项目更适合用来展示大模型应用开发能力，而不是仅仅展示会调用模型 API
